# Debugging → Following the Program

At Weird Mike's Pawn Shop, JavaScript was surprisingly helpful. The program broke, JavaScript complained, and the error message gave you somewhere to start.

This time, JavaScript is less considerate.

Welcome to the **National Cryptid Census**. It tracks eight suspicious creatures, their regions, and the number of reported sightings for each one.

Run it now. You should see:

```text
======NATIONAL CRYPTID CENSUS======
Records: 8
Confirmed: 5
======REQUESTED RECORD======
No record found for Mothman.
======REGION REPORT======
Region: Northeast
Total sightings: 3
```

The program runs from beginning to end. JavaScript doesn't throw an error.

Unfortunately, three results are wrong:

- Six records are confirmed, not five.
- Mothman is in the data.
- The Northeast records contain fifteen total sightings, not three.

JavaScript did exactly what the code told it to do. Now you need evidence that shows **how** it arrived at the wrong answers.

## Make the program narrate its work

In this chapter, you'll use `console.log()` as a debugging tool. Instead of logging only the finished report, you'll place temporary logs at useful points inside the program. Those logs can show you:

- whether JavaScript reached a particular line,
- which values a function received,
- which items a loop visited,
- what a condition compared,
- and how a value changed along the way.

Each investigation will give you a little less direction about where those logs belong. The goal isn't to scatter logs everywhere. It's to choose checkpoints that help you answer one question:

> **Where does the program's actual behavior first stop matching what I expected?**

You'll work in the same `main.js` from beginning to end. Fix only the problem each lesson asks you to investigate; each correction clears the way for the next trace.

<Callout type="danger" title="Don't fix ahead">
  <p className="m-0">
    You'll probably notice suspicious code before the lesson asks about it. Leave it alone for now. Tracing is most useful when you can connect one symptom to one cause.
  </p>
</Callout>

## The debugging rhythm

Keep returning to the same questions:

1. What should happen?
2. What actually happened?
3. Which function produces that result?
4. What values reach that function?
5. Where do the expected and actual values separate?
6. What is the smallest change that fixes the cause?

You aren't trying to become fast at guessing. You're learning to make the program show you what it is really doing.

## Technical Vocabulary

| Term | Plain-English meaning | Tiny example |
| --- | --- | --- |
| tracing | Following execution or values through a program | Logging the item examined during each loop |
| inspection | Looking closely at values at a chosen point in the program | Logging `cryptid.name` before a condition |
| expected behavior | What the program is supposed to do | Report six confirmed records |
| actual behavior | What the program really does | Report five confirmed records |
| evidence | Information that helps narrow down a cause | A trace showing that a loop never reached the final record |
