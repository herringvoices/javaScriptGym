# Debugging → Finding What Went Wrong

Sooner or later, every program does something you did not mean for it to do.

Sometimes JavaScript stops running and prints a bright red error message. Sometimes nothing crashes at all, but the result is still wrong. A label is swapped. A total is off. An item disappears from a list.

The computer followed the instructions it was given. Unfortunately, those instructions were not quite the ones you intended.

That is a **bug**.

**Debugging** is the process of figuring out why a program's actual behavior does not match the behavior you expected, then correcting the problem.

A useful debugging rhythm is:

1. **Run** the program.
2. **Observe** what actually happens.
3. **Compare** that with what should happen.
4. **Investigate** the difference.
5. **Change** the code.
6. **Run again** to see whether your change actually fixed the problem.

That order matters.

Changing code before you understand what went wrong is mostly guessing. Sometimes the guess works. Sometimes you turn one bug into three, which is a fun way to spend an afternoon if your afternoon was going suspiciously well.

## Bugs do not always come with error messages

Consider this program:

```js
const firstName = "Mina";
const lastName = "Lopez";

console.log(`First name: ${lastName}`);
console.log(`Last name: ${firstName}`);
```

JavaScript can run this code without a problem. The syntax is valid. Nothing crashes.

But look at the output:

```text
First name: Lopez
Last name: Mina
```

That is not what the programmer intended.

The **expected behavior** was:

```text
First name: Mina
Last name: Lopez
```

The **actual behavior** was different.

That difference is the bug.

This distinction is important because JavaScript cannot always tell you when your program is wrong. It can tell you when it cannot understand or perform an instruction, but it does not know what you *meant* your program to do.

That part is your job.

## Errors are evidence

Other bugs are easier to notice because JavaScript stops the program and reports an **error**.

At first, an error message can look like a wall of red text standing between you and a working program. But an error message is not just a complaint. It is information.

It can tell you things like:

- what kind of problem occurred,
- where JavaScript noticed the problem,
- and which parts of your code were involved.

A debugger learns to treat that information as **evidence**.

Instead of asking:

> How do I make this error disappear?

you want to start asking:

> What is this telling me about what went wrong?

That is what this module is about.

You will learn how to read JavaScript's error messages, follow stack traces, inspect a running program, pause your code with breakpoints, and trace values through a program step by step.

## Technical Vocabulary

| Term | Plain-English meaning | Tiny example |
| :--- | :--- | :--- |
| bug | A problem that causes a program to behave differently from what was intended | A total displays <code>12</code> when it should display <code>15</code> |
| debugging | Finding the cause of a bug and correcting it | Tracing where the wrong total came from |
| expected behavior | What the program is supposed to do | <code>First name: Mina</code> |
| actual behavior | What the program really does when it runs | <code>First name: Lopez</code> |
| error | A problem JavaScript detects while reading or running your code | <code>TypeError</code>, <code>ReferenceError</code> |
| error message | Information JavaScript provides about an error | <code>ReferenceError: total is not defined</code> |
| evidence | Information you can use to narrow down the cause of a bug | Output, error messages, variable values |
