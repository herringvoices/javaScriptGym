# State & DOM → Element Selection & Manipulation

If we tried to build a simple social media app with “just HTML,” it would go sideways fast.

Imagine your page has a list of posts:

A user creates a post → you now need to add new HTML to the page.

A user deletes a post → you now need to find the right post in the HTML and remove it.

A user edits a post → you now need to find the right spot and replace the right text.

That’s doable… but it’s also how you end up with code that feels like:

“Where do I even put the HTML?”
“Why didn’t the screen update?”
“Why did the wrong thing update?”

The better approach is to flip the responsibility:

Instead of hand-editing HTML every time data changes, you let your data decide what the page should show, and you render the page from that data.

That’s what this standard is about.

---

## The big idea

Your web page has two “worlds”:

- Your data (arrays/objects that represent what’s true right now)
- The DOM (the browser’s live page content — what the user sees)

Your job is to keep those worlds in sync.

When the data changes, you update what the DOM shows.

---

## What you’ll practice in this standard

You’ll build the core “rendering pipeline” that most web apps rely on:

- Selecting elements using getElementById, querySelector, and querySelectorAll
- Updating element content using textContent and innerHTML
- Using a single mount point (like #app) as the place your UI is rendered

## The tiny project

Boarblemish Academy needs a cafeteria screen.

When the page loads, it briefly says Loading…
Then it shows a header and a list of student profile cards.

You’re going to build the pipeline that makes that possible:

- Find the mount point (#app)
- Render a page “shell” into the DOM (header + container)
- Generate HTML strings from data (your first “components”)
- Inject those strings into the page
