# Change → Filter → Re-render

Last section, you got the dropdown working and proved your `change` handler fires by logging `event.target.value`.

Now you’re going to do the real version of that move:

**Use the selected value to change what’s rendered on the page.**

That’s the whole goal here. Not “state management.” Not “sync.” Not “architecture.”

Just the core interaction loop:

- user changes a control
- browser fires an event
- your handler reads the value
- your code renders the correct list

---

## The idea: filter the data first, then render the list

When beginners try to filter a list, the first impulse is usually:

> “I’ll hide some `<li>`s.”

That can work… but it’s not the clean move you’re practicing here.

The clean move is:

1. Decide which data should be visible
2. Render *only that* data into the list container

So your list is always “freshly built” from the data you chose.

---

## Canonical snippet: filter-driven render (neutral example)

Imagine a list of quests, each with a `difficultyId`, and a dropdown that selects difficulty.

```js
const quests = [
  { id: 1, title: "Gather herbs", difficultyId: 1 },
  { id: 2, title: "Slay the ogre", difficultyId: 3 },
  { id: 3, title: "Escort the merchant", difficultyId: 2 }
];

const renderQuestList = (difficultyId) => {
  const filtered = difficultyId === 0
    ? quests
    : quests.filter(q => q.difficultyId === difficultyId);

  document.querySelector("#questList").innerHTML =
    "<ul>" + filtered.map(q => `<li>${q.title}</li>`).join("") + "</ul>";
};
```

### What’s happening here?

1. The render function accepts a filter value (`difficultyId`).
2. If it’s `0`, we show everything.
3. Otherwise, we use `filter()` to choose only matching quests.
4. We map the filtered array into `<li>` strings.
5. We inject the markup into the DOM.

This pattern scales well because it keeps one rule true:

> The DOM list is always the result of rendering your chosen data.

---

## DOM values are strings (so compare like a grownup)

Here’s the practical reality:

- `event.target.value` comes from the DOM
- DOM values are strings

So even if your options look numeric, they arrive as text:

- `"0"`, `"1"`, `"2"`, …

And strict comparisons care:

- `"2" === 2` is `false`

So before you use the value for numeric comparisons, convert it:

```js
const selectedId = parseInt(event.target.value);
```

You’re not doing this because “parsing is fun.”

You’re doing it because you want comparisons like:

```js
p.schoolId === selectedId
```

to actually work.

---

<Callout type="tip" title="Parse once, then stop thinking about it">
  <p>A common beginner mistake is mixing string ids and number ids throughout the code.</p>
  <p>The clean habit is:</p>
  <ul>
    <li>read from the DOM (string)</li>
    <li>parse immediately (number)</li>
    <li>use the parsed number everywhere else</li>
  </ul>
  <p>That way your filtering logic stays simple and predictable.</p>
</Callout>

## Recap

You can now:

- Use a `change` event to drive real UI updates
- Parse DOM string values into numbers for reliable comparisons
- Filter an array based on a selected id
- Re-render a list from filtered data instead of manually hiding DOM nodes
- Combine event handling and rendering into a clean, repeatable loop

That’s the heart of interactive UI: **listen → read → decide → render.**

---

## Technical Vocabulary

| Term           | Meaning                                                                 |
| -------------- | ----------------------------------------------------------------------- |
| `filter()`     | Creates a new array containing only items that match a condition.       |
| parse          | Converting a string into a number so it can be compared mathematically. |
| re-render      | Updating what’s on screen by running your render logic again.           |
| `change` event | Fires when a form control’s value changes (like a dropdown).            |
| argument       | A value passed into a function so it can behave differently.            |
