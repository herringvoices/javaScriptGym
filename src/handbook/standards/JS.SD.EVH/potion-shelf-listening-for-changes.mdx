# Listening for Changes

Click events are great when the user chooses something by… well… clicking it.

But a lot of UI choices aren’t “click the page.” They’re:

- pick an option from a dropdown
- toggle a checkbox
- type into an input

Those controls have their own events. Today’s focus is the simplest and most common one:

**The `change` event.**

Your goal in this section is very specific:

**Create a dropdown from data, attach a `change` listener to the dropdown itself, and read `event.target.value`.**

Not filtering yet. Not re-rendering the list yet.

Just: **change → read value → prove it works.**

---

## The idea: listeners don’t have to live on `document`

So far, you’ve attached a click listener to `document`. That’s useful when you want to hear clicks anywhere.

But for form controls, the most direct approach is usually:

1. Select the element you care about
2. Attach a listener to that element
3. Read values from that element when the event fires

That’s the new move: **attach the listener to the specific element.**

---

## Canonical snippet: `change` + `event.target.value`

Imagine a dropdown that lets the user choose a difficulty level:

```html
<select id="difficulty">
  <option value="easy">Easy</option>
  <option value="medium">Medium</option>
  <option value="hard">Hard</option>
</select>
```

Then your JavaScript does this:

```js
const select = document.querySelector("#difficulty");

select.addEventListener("change", (event) => {
  console.log(event.target.value);
});
```

When the user selects a different option, the browser fires a `change` event and `event.target.value` gives you the selected option’s value.

---

## Rendering a dropdown from data

A dropdown is a list too. Instead of mapping data into `<li>` elements, you map it into `<option>` elements.

```js
const languages = [
  { id: 1, label: "JavaScript" },
  { id: 2, label: "Python" },
  { id: 3, label: "Ruby" }
];

const options = languages
  .map(lang => `<option value="${lang.id}">${lang.label}</option>`)
  .join("");

document.querySelector("#controls").innerHTML =
  `<select id="languageSelect">${options}</select>`;
```

Same rendering muscle, different HTML tags.

---

<Callout type="tip" title="The value you read is whatever you put in the HTML">
  <p>The browser does not know what your ids mean. It reports the selected option’s <code>value</code>.</p>
  <p>If you render <code>{'<option value="0">All</option>'}</code>, then <code>event.target.value</code> will be the string <code>"0"</code>.</p>
</Callout>

---

## Why we’re logging first

When you learn a new move, you want clear proof that the move works.

Logging is the “proof mode” for event handling:

- you change the selection
- you see the value printed
- you know the event fired and your handler ran

Then, in the next part, you’ll replace the log with visible behavior.

## Recap

You can now:

- Render a dropdown from data by mapping objects into `<option>` strings
- Attach an event listener to a specific element instead of only `document`
- Use the `change` event to react to dropdown selection changes
- Read the selected option’s value using `event.target.value`
