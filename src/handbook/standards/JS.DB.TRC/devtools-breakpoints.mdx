# DevTools → Pause the Census

Temporary logs are useful, but they have limits.

You have to decide what to log before the program runs. Then you change the file, run it, read the output, change the log, and run again.

Sometimes you want to stop the program **while it is running** and look around.

That is what a debugger lets you do.

A **breakpoint** tells the browser:

> When execution reaches this line, pause before continuing.

While the program is paused, you can inspect variables and move through the code one line at a time.

## Find `main.js` in DevTools

Run the Census dashboard, then open Chrome DevTools.

Open the **Sources** panel.

Find the generated `main.js` for your handbook workspace. If the file tree is noisy, use Chrome's file search and search for `main.js`.

The source map for the student file uses a path beginning with:

```text
jsgym://student/handbook/
```

Open the `main.js` that contains the Cryptid Census code.

## Your first breakpoint

Find `matchesFilters()`:

```js
function matchesFilters(cryptid) {
  const matchesRegion =
    state.region === "all" || cryptid.location === state.region;

  const matchesConfirmed =
    !state.confirmedOnly || cryptid.confirmed;

  return matchesRegion && matchesConfirmed;
}
```

Click the line number beside the first `const matchesRegion` line.

A breakpoint marker should appear.

Run the program again.

Execution should pause the first time `matchesFilters()` receives a cryptid.

If an assignment line is highlighted, inspect the variable before and after you step over the line. You can literally watch the value appear.

## The controls you need

For now, you only need a few debugger controls:

- **Resume** continues until the next breakpoint or the end.
- **Step over** executes the current line and pauses at the next line in the current function.
- **Step into** follows a function call so you can inspect what happens inside it.
- **Step out** finishes the current function and returns to its caller.

A useful rule is:

> **Step over when you trust a function and care about its result. Step into when you suspect the function itself.**

When paused, use **Scope** to inspect variables in the current function. You can also hover a variable in the source code to see its current value.

## Step into a function

There is one more move worth practicing before you need it.

Set a breakpoint inside `render()` on:

```js
const visibleCryptids = getVisibleCryptids();
```

Run again.

This time, use **Step into** when JavaScript is about to call `getVisibleCryptids()`.

You should move into that function instead of skipping directly to its returned value.

You do not need to change any code.

The point is to feel the difference:

- Step over: "Give me the result."
- Step into: "Show me how this function gets the result."

That choice becomes useful immediately.

---

## The tracing habit

From here forward, do not step mindlessly.

Before executing an important line, ask:

> What do I expect this line to do?

Then step.

Ask:

> What did it actually do?

The first place those answers differ is usually very close to the bug.
