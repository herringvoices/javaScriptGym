# Event Inspection → The Picky Cryptid Card

Turn **Confirmed only** back off.

Click the empty space inside Bigfoot's card.

The details panel works.

Now click directly on the word **Bigfoot**.

The program can crash.

That is strange until you reproduce it carefully:

- some clicks on the card work,
- some clicks on the same card fail.

You already know what to do with a repeatable error: read the error and use the stack trace as evidence.

But the line where the program finally crashes is not necessarily where the bad value began.

This time, trace backward.

## What did you actually click?

The handler begins with:

```js
cryptidList.addEventListener("click", (event) => {
  const id = Number(event.target.dataset.id);

  state.selectedId = id;
  renderDetails();
});
```

The important value is `event.target`.

It is the specific element that received the click.

A cryptid card contains several nested elements:

```html
<button class="cryptid-card" data-id="1">
  <strong>Bigfoot</strong>
  <span>Pacific Northwest</span>
  <span>CONFIRMED</span>
</button>
```

Click the button's empty space and the target can be the button.

Click the word Bigfoot and the target is the `<strong>` inside the button.

Only the button has `data-id`.

The starter code already includes this helper:

```js
function findCryptidCard(element) {
  return element.closest(".cryptid-card");
}
```

You do not need to write a new DOM technique here. That helper's job is to take the exact clicked element and find the surrounding cryptid card.

Your job is to prove why the current value is wrong, then use the existing helper in the event flow.

Notice how ERR and TRC worked together here.

The stack trace showed you where the bad value finally caused a failure.

Tracing showed you where that bad value entered the program.

Those are not competing debugging techniques. They are different pieces of evidence.
