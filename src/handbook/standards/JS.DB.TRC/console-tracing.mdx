# Console Tracing → Follow the Program

Sometimes a program runs without an error and still produces the wrong result. JavaScript can't tell you the result is wrong because it doesn't know what you intended.

When that happens, `console.log()` can do more than print the finished output. You can place temporary logs **inside** the program to make some of its hidden behavior visible.

That practice is called **console tracing**.

## A log is a checkpoint

Every strategically placed log is a checkpoint. When its message appears, you learn two things:

- JavaScript reached that part of the program.
- The values in the log had those values at that moment.

Consider this small function:

```js
function formatPackageName(packageName) {
  const trimmedName = packageName.trim();
  const label = trimmedName.toUpperCase();
  return label;
}

formatPackageName("  board games  ");
```

You could see how the function reaches its answer by adding a few temporary logs:

```js
function formatPackageName(packageName) {
  console.log(`received: [${packageName}]`);

  const trimmedName = packageName.trim();
  console.log(`after trim: [${trimmedName}]`);

  const label = trimmedName.toUpperCase();
  console.log("returning:", label);
  return label;
}

formatPackageName("  board games  ");
```

The trace would show:

```text
received: [  board games  ]
after trim: [board games]
returning: BOARD GAMES
```

The logs don't change the formatting. They let you watch the value move through the function.

## A loop creates repeated checkpoints

When a log is inside a loop, JavaScript prints a new message each time it reaches that line. Include the loop number and the current value so every message tells you which pass produced it.

```js
const packages = ["board games", "desk lamp", "typewriter"];

for (let i = 0; i < packages.length; i++) {
  console.log(`Loop ${i + 1}: checking ${packages[i]}`);
}
```

The trace would show:

```text
Loop 1: checking board games
Loop 2: checking desk lamp
Loop 3: checking typewriter
```

The loop still uses `i` to access array positions `0`, `1`, and `2`. The `i + 1` in the message only gives each pass a more natural label for a person reading the console.

Now the trace can answer a useful question: **Which values did this loop actually reach?** If an expected package never appears, you have evidence that the loop didn't visit it.

<Callout type="tip" title="Why the order tells a story">
  <p className="m-0">
    Remember: once JavaScript starts running a file, it generally works from top to bottom, one statement at a time. A loop sends it back through the same statements for each item. Because each <code>console.log()</code> prints when JavaScript reaches it, the messages appear in the same order as the path JavaScript took through the program.
  </p>
</Callout>

## Start with a question

Don't scatter logs everywhere and hope one looks suspicious. Decide what you need to learn, then place a log where it can answer that question.

| Question | Useful place to log |
| --- | --- |
| Did this function run? | At the beginning of the function |
| Which items did this loop visit? | Inside the loop |
| What value reached this condition? | Immediately before the condition |
| How did this value change? | Before and after the line that updates it |
| What is the function about to return? | Immediately before `return` |

Run the program, read the messages in order, and find the first place where the trace stops matching what you expected.

<Callout type="tip" title="Temporary means temporary">
  <p className="m-0">
    A tracing log is a tool, not part of the finished program. Add it to answer a question, use the evidence, and remove it after you've found the cause.
  </p>
</Callout>

## What the trace gave you

The wrong final number was only a symptom. Your logs exposed the steps that produced it, so you could find where the program's actual behavior first separated from what you expected.
