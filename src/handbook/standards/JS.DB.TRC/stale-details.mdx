# Independent Debugging → The Ghost in the Details Panel

The obvious crashes are gone.

The counts work.

The filters work.

The cards work.

There is one last problem.

Follow these steps exactly:

1. Choose **All regions**.
2. Make sure **Confirmed only** is off.
3. Select **Bigfoot** so its details appear.
4. Change the region to **Northeast**.

The Records list now contains only:

- Jersey Devil
- Dover Demon

But the Details panel still shows Bigfoot.

Bigfoot is not visible anymore, but the application still considers it selected.

Nothing throws an error.

No single line is obviously illegal.

This is the kind of bug where tracing matters most.

## You choose the evidence

For this investigation, you are not being told where to place a breakpoint.

Use the tools you have learned:

- add a temporary `console.log()`,
- set a breakpoint,
- inspect Scope,
- Step over,
- Step into,
- reproduce the bug again.

Useful questions include:

- What does `getVisibleCryptids()` return after Northeast is selected?
- What is `state.selectedId` at that moment?
- Does `renderDetails()` know which records are currently visible?
- At what point should a hidden selection stop being a valid selection?

  const visibleCryptids = getVisibleCryptids();

  const selectedCryptidIsVisible = visibleCryptids.some(

  );

  if (state.selectedId !== null && !selectedCryptidIsVisible) {
    state.selectedId = null;
  }

  renderSummary(visibleCryptids);
  renderCryptids(visibleCryptids);
  renderDetails();
}`}</pre>

Your Census dashboard should now behave like this:

## Technical Vocabulary

| Term | Plain-English meaning | Tiny example |
| --- | --- | --- |
| trace | Follow execution or values through a program | Log each loop item or step through a function |
| breakpoint | A place where DevTools pauses execution before a line runs | Pause inside `matchesFilters()` |
| Step over | Run the current line without following a called function | Execute an assignment and move to the next line |
| Step into | Follow a function call into that function | Enter `getVisibleCryptids()` from `render()` |
| Step out | Finish the current function and return to its caller | Leave a helper after inspecting it |
| Scope | The variables and values available where execution is paused | Inspect `cryptid` and `state` |
| state | Data that represents the program's current situation | `state.region`, `state.selectedId` |
| stale UI | Screen output that no longer matches current state | Bigfoot remains in Details after being filtered out |

## Wrap up

In ERR, JavaScript told you something had gone wrong.

In this project, you often had to discover the problem yourself.

You used `console.log()` when you needed a quick trace. You used breakpoints when you needed to freeze execution. You stepped through code, inspected variables, followed bad values backward, and compared program state with what the screen showed.

The core habit is simple:

> **Predict. Observe. Compare.**

Find the first place where what you expected and what actually happened stop matching.

At this point, `main.js` is also doing a lot: data, filtering, rendering, formatting, and event handling all live together.

That is a different kind of problem.

Next, you will start learning how to organize growing programs into clearer pieces.
