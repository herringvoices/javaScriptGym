# Reproducing Errors → Make It Happen on Purpose

The final error should look familiar:

```text
TypeError: item.name.toUpperCase is not a function
```

You already know what a `TypeError` is.

You know how to find the line where it happened.

But before you fix this one, do something different.

Make sure you can make it happen **reliably**.

A bug is much easier to investigate when you can **reproduce** it: make the same failure happen again under known conditions.

At the bottom of Mook's program, one value controls which inventory item gets printed:

```js
const requestedItemId = 4;
const requestedItem = inventory.find((item) => item.id === requestedItemId);
printItem(requestedItem);
```

That gives you an experiment.

Keep the rest of the program the same and change only `requestedItemId`.

Try `1`. Run.

Then `2`.

Then `3`.

Then `4`.

## An example is not yet a condition

You should find that IDs `1`, `2`, and `3` print successfully.

ID `4` produces the error.

"The program breaks on item 4" is useful because you can reproduce it.

But you can do better.

Compare item 4 with the items that work and ask:

> **What is different about the value that reaches `formatItemName()`?**

You moved from:

- **"The program throws a TypeError."**
- to **"The program throws it when I request item 4."**
- to **"The program throws it when the requested item's name is not a string."**

That last statement describes the **condition**, not just one example.

And that is the point of reproduction: turn a mysterious failure into something specific enough to test.

---

Mook gave you one broken file.

You never replaced it with a fresh exercise. You kept running the same program and used each failure as evidence for what to investigate next.

Your debugging rhythm was:

1. Read the error type.
2. Use its location to narrow your search.
3. Follow stack frames when the bad value came from somewhere else.
4. Reproduce a failure to identify the condition that triggers it.
5. Make one change and run again.

And along the way, something important happened over and over:

> **A new error meant the program got farther.**

In the next debugging standard, the program will not always be kind enough to throw an error. You will trace values and execution while the code runs.
