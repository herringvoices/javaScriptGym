# Reproducing Errors → Make It Happen on Purpose

Mook's program finally runs all the way through. It prints every inventory item, then successfully prints the requested item with ID `1`.

That's good news—but one successful run doesn't prove every input works.

Imagine Mook gives you a new bug report:

> **"Whenever I request item 99, the program crashes."**

Don't start rewriting the program yet. First, make sure you can make the failure happen **reliably**.

A bug is much easier to investigate when you can **reproduce** it: make the same failure happen again under known conditions.

At the bottom of Mook's program, one value controls which inventory item gets printed:

```js
const requestedItemId = 1;
const requestedItem = inventory.find((item) => item.id === requestedItemId);
console.log("======REQUESTED ITEM======");
printItem(requestedItem);
```

That gives you an experiment. Keep the rest of the program the same and change only `requestedItemId`.

Try `1`. Run.

Then `2`, `3`, and `4`.

Finally, try `99`.

## An example is not yet a condition

"The program breaks when I request item 99" is useful because you can reproduce the report. But you can do better.

Compare the successful runs with the failing run and ask:

> **What is different about the value that reaches `printItem()`?**

The answer should describe a condition—not merely repeat one ID that happened to fail.

You moved from a vague symptom, to a repeatable input, to a condition you could test in code.

That is the point of reproduction: turn a mysterious failure into something specific enough to explain, test, and handle.

---

Mook gave you one broken file.

You never replaced it with a fresh exercise. You kept running the same program and used each failure as evidence for what to investigate next.

Your debugging rhythm was:

1. Read the error type.
2. Use its location to narrow your search.
3. Follow stack frames when the bad value came from somewhere else.
4. Reproduce a failure to identify the condition that triggers it.
5. Make one change and run again.

And along the way, something important happened over and over:

> **A new error meant the program got farther.**

In the next debugging standard, the program won't always be kind enough to throw an error. You'll trace values and execution while the code runs.
