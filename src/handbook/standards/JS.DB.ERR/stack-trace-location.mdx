# Stack Traces → Find the Failure

After fixing `inventory.length`, the program prints three lines successfully.

Then another `TypeError` appears.

This one points into a function:

```text
TypeError: Cannot read properties of undefined (reading 'toUpperCase')
    at printDescription (main.js:LINE:COLUMN)
    at main.js:LINE:COLUMN
```

Your exact line and column numbers may differ. That is fine. Those numbers are there to help you find the code that failed.

The lines underneath the error message are the **stack trace**.

A line such as:

```text
at printDescription (main.js:LINE:COLUMN)
```

is a **stack frame**.

It tells you:

- which function was running,
- which file contains the code,
- and the line and column where JavaScript failed.

When you are debugging your own code, the first frame that points into your readable student file is usually the best place to start.

In desktop Chrome DevTools, the same authored files appear under <code>student</code> in <strong>Sources</strong>; the <code>generated</code> and <code>jsgym-internal</code> sources are runner machinery, not the code you wrote.

The important habit is simple:

> **Read the location before you start scanning the file.**

The first useful frame sends you here:

```js
function printDescription(item) {
  console.log(item.descripton.toUpperCase());
}
```

The error says JavaScript tried to use `toUpperCase` on `undefined`.

That gives you two pieces of evidence:

1. the stack trace tells you **where** the failure happened,
2. the error tells you **what kind of value caused it**.

The stack trace did more than say "something broke."

It gave you a direct route to the failure.

On the next run, the first frame still tells you where JavaScript notices the problem. But this time, the mistake you need to fix is somewhere else in the call chain.
