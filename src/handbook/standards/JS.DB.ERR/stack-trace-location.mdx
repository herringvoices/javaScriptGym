# Stack Traces → Follow the Call Chain

After fixing `inventory.length()`, the program makes it as far as:

```text
======INVENTORY======
```

Then JavaScript stops with another error. Click **Stack trace** to expand the information underneath it:

```text
TypeError: Cannot read properties of undefined (reading 'toUpperCase')
/main.js:35:20
▼ Stack trace
formatItemName — /main.js:35:20
printItem — /main.js:43:18
(anonymous) — /main.js:52:3
▶ Raw browser stack
```

You already know how to read the error message: JavaScript tried to use `toUpperCase()` on `undefined`. You also know that `/main.js:35:20` points to the file, line, and character where it happened.

The expanded stack trace gives you something new: the chain of function calls that brought the program to that location.

## Stack traces and stack frames

A **stack trace** is a list of locations JavaScript was working through when an error happened. Each line in that list is a **stack frame**.

Start with the first frame:

```text
formatItemName — /main.js:35:20
```

It tells you that JavaScript was inside `formatItemName()` when it failed. The function is in `main.js`, and the failure happened on line `35`, character `20`.

The next frame tells you where `formatItemName()` was called:

```text
printItem — /main.js:43:18
```

Line `43` is the **call site**: the place inside `printItem()` where the program called `formatItemName()`.

That caller can be just as useful as the failure location, especially when a function is called more than once.

Take this code for example:

```js
function capitalize(str) {
  return str.toUpperCase();
}

capitalize("i'm a string!");
capitalize(24);
```

That second call would produce a `TypeError`. Its stack trace would look something like:

```text
TypeError: str.toUpperCase is not a function
capitalize — /main.js:2:17
(anonymous) — /main.js:6:1
```

Both calls reach the same line inside `capitalize()`, but only the second one fails. The first stack frame points inside the function, where JavaScript finally breaks. The next frame points back to the particular call that passed in `24`.

The parameter may be named `str`, but the argument in that second call is still a number. `toUpperCase()` is a string method, so the number can't use it.

## Follow this call chain

The trace starts where JavaScript failed, then works backward through the calls that led there. Read this one from the first frame downward:

1. `formatItemName()` is where JavaScript failed.
2. `printItem()` called `formatItemName()`.
3. The main body of `main.js` called `printItem()`.

That sequence is the **call chain**.

Start by inspecting the function in the first frame:

```js
function formatItemName(item) {
  return item.name.toUpperCase();
}
```

That code works when `item` is one inventory object with a string `name`. So don't immediately rewrite the function. Ask:

> **What value did its caller give it?**

Then move down one frame and inspect that call. If the value was already wrong there, move down again. At each step, compare the argument being passed with the kind of value the next function expects.

<Callout type="tip" title="The first frame is a starting point, not always the fix">
  <p className="m-0">
    The first frame shows where a bad value finally caused an error. A later frame may show where that value entered the call chain. Follow the value backward before deciding which line needs to change.
  </p>
</Callout>

## Wrap up

A stack trace is JavaScript saying, roughly:

> **"Here's where I failed, and these are the calls that brought me here."**

Use the first useful frame to find the failure. Then follow the remaining frames through the callers when you need to trace a value back toward its source.
