# Modules → Rebuild the Architecture

The National Cryptid Census now has three JavaScript modules:

```text
main.js
data.js
census.js
```

It also has two diagrams that you built a few lines at a time.

Now you are going to prove that you can derive those diagrams from the code instead of remembering the previous answers.

## Start from the source code

Clear the contents of:

```text
/dependencyGraph.mmd
/sequenceDiagram.mmd
```

Do not change the JavaScript.

Then rebuild both diagrams by inspecting the finished project.

## Rebuild the dependency graph

Use the algorithm you learned:

1. list the modules,
2. inspect each import statement,
3. identify the importer,
4. identify the module named by the path,
5. draw one arrow for each module dependency.

Your graph should answer only:

> Which module relies on which other module?

Do not draw one arrow per imported function.

## Rebuild the sequence diagram

Then read `main.js` in execution order.

For every call from `main.js` into `census.js`:

1. draw the call arrow,
2. show the repeated work inside `census.js` with a `loop` block,
3. draw the returned result,
4. continue downward to the next cross-module call.

Your sequence diagram should answer:

> What happens across these modules, and in what order?

## One final consistency check

When you finish, compare three artifacts:

- the JavaScript modules,
- the dependency graph,
- the sequence diagram.

They should tell compatible versions of the same story.

## What you can do now

You started with one working file.

You can now:

- move data or functions into separate modules without changing program behavior,
- export several values by name,
- import the exact names another module provides,
- debug broken module paths and mismatched named imports,
- derive a dependency graph from import relationships,
- write a sequence diagram from execution order,
- show repeated work with sequence-diagram loop blocks,
- and check whether code and diagrams still describe the same system.

The next Modules & Organization standard asks a larger architectural question:

> Once a project has many files, how should those files be grouped and named so another developer can predict where things belong?

That is project structure.
