# Modules → Multiple Named Exports

## One module can export several names

A module is not limited to one export.

Imagine a `formatters.js` module with two related helpers. It can export both names together:

```js
export {
  formatTitle,
  formatRuntime,
};
```

That is still one idea: **named exports**.

Each name inside the braces is something another module is allowed to import.

Another module can request those exact names:

```js
import {
  formatTitle,
  formatRuntime,
} from "./formatters.js";
```

The braces do not mean "one object." They are the syntax JavaScript uses to list named exports and named imports.

## Keep imports readable

Once an import gets long, putting one name on each line makes the relationship easier to scan.

For example:

```js
import {
  formatTitle,
  formatRuntime,
} from "./formatters.js";
```

The importing file can now use either function while the formatting operations stay together in one module.

Use that pattern to decide how the remaining Census operations should cross the existing module boundary.

## Why the graph does not change

`main.js` imported one function from `census.js` before.

Now it imports three.

The number of imported names changed, but the module relationship did not:

```text
main.js depends on census.js
```

A dependency graph usually shows module-to-module relationships, not one arrow per imported function.

Now that the project structure is visible, we can ask a different question: what happens across those module boundaries when the program actually runs?
