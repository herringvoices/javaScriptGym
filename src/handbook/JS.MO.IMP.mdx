# National Cryptid Census · Modules

You already know this program.

In the debugging unit, the National Cryptid Census gave you several quiet bugs. You traced loops, inspected decisions, followed values, and repaired the report until it produced the right results.

Now the program works.

That is exactly why we are going to change it.

Not because the Census needs a new feature. Not because anything is broken. We are going to reorganize the same working program so that each file has a clearer job.

## One file is doing every job

Open `/main.js`.

You can divide the file into three broad sections:

1. **Data** - the `cryptids` array.
2. **Reusable operations** - functions such as `countConfirmed()` and `findCryptidByName()`.
3. **Application logic** - the code that chooses what to request and prints the report.

Those sections can live in one file. JavaScript does not mind.

People eventually do.

## Why modules?

Splitting code into more files is not automatically better. Fifty mystery files can be every bit as confusing as one enormous file.

The goal is to give each file a clear job.

### They make code easier to read

When everything lives in `main.js`, finding one function means scrolling past the data, the other functions, and the code that prints the report.

Once those responsibilities are separated, the filenames become a map:

- Look in `inventory.js` for a shop's products.
- Look in `prices.js` for the functions that calculate prices.
- Look in `main.js` to see how the complete program is put together.

You can focus on the part you need without holding the entire program in your head at once.

### They separate different concerns

The data, reusable operations, and application logic are related, but they do different jobs. Keeping those jobs separate is called **separation of concerns**.

That separation makes changes easier to reason about. If the shape of a product changes, you know where the data lives. If a total is wrong, you know where the calculation lives. If the report needs another section, you know where the program is assembled.

Instead of asking, “Where in this giant file is the code I need?” you can ask, “Which part of the program owns this job?”

### They make code easier to reuse

A useful function should not have to be copied every time another part of the project needs it. A module can export that function once, and other modules can import it where they need it.

That gives the project one shared version of the function instead of several copies that can drift apart.

### They help teams stay out of one another's way

Imagine three developers working in one giant `main.js`. One edits the data, one repairs a Census function, and one changes the report. Even when they are working on different ideas, they are changing the same file. When Git tries to combine their work, those edits are more likely to collide.

Modules let teammates work in different parts of the project. They do not make merge conflicts impossible, but they reduce unnecessary overlap and make it clearer who is changing what.

That becomes increasingly valuable as both the program and the team grow.

Modules let us create those boundaries without changing what the program does.

A **module** is a JavaScript file with its own code and its own scope. Code in one module is not automatically available inside another module.

That boundary creates the problem this unit will teach you to solve:

> How do separate files share the specific data and functions they need?

The answer is **named exports and named imports**.

## The rule for this project

We are refactoring, not redesigning the Census.

After each code change, run the program again. Its output should remain:

```text
======NATIONAL CRYPTID CENSUS======
Records: 8
Confirmed: 6
======REQUESTED RECORD======
Name: Mothman
Region: Appalachia
Sightings: 19
======REGION REPORT======
Region: Northeast
Total sightings: 15
```

If moving code changes the result, the refactor is not finished yet.

## Two diagrams will grow with the code

Splitting one file into several files makes the project easier to organize, but it also gives your working memory more places to track.

So you will maintain two visual models as the project changes.

### Dependency graph

A dependency graph answers:

> **Which module relies on which other module?**

You will build it in `/dependencyGraph.mmd`.

### Sequence diagram

A sequence diagram answers:

> **What happens, and in what order, when the program runs?**

You will build it in `/sequenceDiagram.mmd`.

These diagrams are not decorations at the end of the unit. You will write them as your project changes and preview them inside the workbench.

By the end, you should be able to move code between modules, reconnect it with imports and exports, draw the module dependencies, and trace the important runtime interactions across those module boundaries.

Start with the easiest responsibility to separate: the data.
